## 1. 汇编器与汇编过程 Assemblers

> 基础概念见 [[计算机笔记/06-汇编与工具链\|06-汇编与工具链]]

### 汇编器的工作

**汇编器**把**汇编代码 → 机器码**（一对一翻译，和编译器不同）

```
汇编代码（.s / .asm）          机器码（.o / .obj）
MOV R0, #5          ──►  1010 00000101
ADD R1, R0, #3     ──►  0011 00000011
HLT                 ──►  0000 00000000
```

### 两遍扫描 Two-Pass Assembly

汇编器需要**两遍**才能完成翻译：

```
第一遍 (Pass 1)：
  ─ 扫描所有指令，计算每条指令的地址
  ─ 构建符号表 Symbol Table（标签 → 地址）

第二遍 (Pass 2)：
  ─ 用符号表替换标签
  ─ 生成机器码

为什么需要两遍？
  因为前向引用：JMP loop 中的 loop 在后面定义
  第一遍不知道 loop 的地址 → 先记在符号表
  第二遍用符号表填上地址
```

### 两遍扫描示例

```assembly
    地址  指令
    0     JMP start      ; 第一遍：不知道 start 地址
    1                     ; 第二遍：查符号表 → start = 3
    2     start:          ; 第一遍：记下 start = 2
    3     LDI #5
    4     HLT
```

```
第一遍结束后符号表：
  start → 2

第二遍：JMP start → JMP 2
```

### 汇编器 vs 编译器

| 对比 | 汇编器 Assembler | 编译器 Compiler |
|:-----|:----------------|:----------------|
| **输入** | 汇编代码 | 高级语言（C/Rust...）|
| **输出** | 机器码 | 汇编代码 |
| **翻译比例** | 1 条指令 → 1 条机器码 | 1 行代码 → 多条机器码 |
| **复杂性** | 相对简单 | 非常复杂（语法分析/优化/代码生成）|

## 2. 编译器 Compilers

### 编译器架构

```
源代码 Source Code
    │
    ▼
┌─────────────────┐
│  前端 Frontend  │  语言相关
│  词法分析       │  Lexical Analysis（token 化）
│  语法分析       │  Syntax Analysis（AST 构建）
│  语义分析       │  Semantic Analysis（类型检查）
└────────┬────────┘
         ▼
┌─────────────────┐
│  中间表示 IR    │  语言无关
│  (LLVM IR /     │
│   Three-Address │
│   Code)         │
└────────┬────────┘
         ▼
┌─────────────────┐
│  后端 Backend   │  机器相关
│  指令选择       │  Instruction Selection
│  指令调度       │  Instruction Scheduling
│  寄存器分配     │  Register Allocation
│  代码生成       │  Code Generation
└────────┬────────┘
         ▼
   汇编代码 Assembly
```

### 三地址码 Three-Address Code (TAC)

编译器常用的中间表示形式：

```
每条指令最多三个地址（两个操作数 + 一个结果）

例：a = b + c * d

TAC 表示：
  t1 = c * d      ; 临时变量 t1 = c * d
  a  = b + t1     ; a = b + t1
```

### 编译器优化 Compiler Optimizations

| 优化 | 说明 | 例子 |
|:-----|:-----|:------|
| **常量折叠 Constant Folding** | 编译期计算常量表达式 | `a = 3 + 5` → `a = 8` |
| **常量传播 Constant Propagation** | 常量替换变量 | `x = 5; y = x + 3` → `y = 8` |
| **死代码消除 Dead Code Elim** | 删除无用代码 | 删掉结果从未使用的代码 |
| **强度削弱 Strength Reduction** | 用廉价操作替代昂贵操作 | `x * 2` → `x << 1` |
| **循环不变式外提 Loop Invariant** | 把不变计算移到循环外 | |
| **函数内联 Inlining** | 函数调用处直接替换为函数体 | |
| **公共子表达式消除 CSE** | 复用已计算过的表达式 | |

### ⚠️ 什么不是优化？ What is NOT an optimisation?

| 操作 | 影响执行时间？ | 原因 |
|:-----|:-------------|:------|
| **删除注释 / Removing comments** | ❌ 不影响 | 注释在词法分析阶段被剥离，根本不进入 AST/IR，不影响生成的机器码 |
| **删除空白 / Removing whitespace** | ❌ 不影响 | 同理，空白在 tokenize 时被忽略 |
| **变量重命名 / Renaming variables** | ❌ 不影响 | 寄存器分配和代码生成不依赖变量名 |

> **考试陷阱**："Removing comments from source code improves the running time of the compiled program." → **False**（这是混肴了"编译时"和"运行时"——注释不影响运行速度！）

## 3. 优化编译器 Optimising Compilers

### -O0, -O1, -O2, -O3 的区别

```
-O0: 不优化，编译最快，适合调试
-O1: 基本优化（减少代码大小 + 基本优化）
-O2: 大部分优化（不包括以空间换时间的）
-O3: 激进优化（包括函数内联、循环展开等）
-Os: 优化代码大小（比 -O2 更小）
```

### 循环优化 Loop Optimizations

```
循环展开 Loop Unrolling（减少循环控制开销）：
  原始：                   展开 2 次：
  for i=0 to 3             for i=0 to 1
    a[i] = 0                 a[i*2] = 0
                              a[i*2+1] = 0

循环分拆 Loop Splitting：
  原始：                   分拆：
  for i=0 to N              for i=0 to mid-1
    if a[i] > 0               proc_pos(a[i])
      proc_pos(a[i])       for i=mid to N
    else                      proc_neg(a[i])
      proc_neg(a[i])

循环交换 Loop Interchange（优化 Cache 局部性）：
  // 按行遍历（空间局部性好）  // 按列遍历（空间局部性差！）
  for i in rows               for j in cols
    for j in cols               for i in rows
      a[i][j] = 0                a[i][j] = 0
```

### 编译器优化与时间 Compiler Optimisations for Time

> 你反馈的考点："编译器中将计算的算了对于时间的优化"

编译器优化通过影响 **Iron Law** 的三个因子来减少执行时间：

```
Time = Instructions × CPI × ClockCycleTime
```

| 优化 | 影响哪个因子 | 说明 |
|:-----|:------------|:------|
| **常量折叠 / Constant folding** | ↓ 指令数 | 编译期算好 `3+5` → `8`，省掉一条加法指令 |
| **常量传播 / Constant propagation** | ↓ 指令数 | `x=5; y=x+3` → `y=8`，消除变量读取 |
| **死代码消除 / Dead code elimination** | ↓ 指令数 | 删掉结果从未被使用的代码 |
| **强度削弱 / Strength reduction** | ↓ CPI | `x*2` → `x<<1`，移位比乘法快 |
| **循环不变式外提 / Loop invariant** | ↓ 指令数 | 把不变计算移到循环外，减少重复执行 |
| **指令调度 / Instruction scheduling** | ↓ CPI | 重排指令减少流水线 stall |
| **循环展开 / Loop unrolling** | ↑ 指令数 但 ↓ CPI | 指令数变多但减少分支开销，总时间可能减少 |

> **关键 insight**：优化目标是最小化**总时间**，不是最小化指令数！
> 循环展开就是典型例子：指令数↑，但 CPI↓，总时间反而↓

## 4. 寄存器分配 Register Allocation

### 为什么需要寄存器分配？

寄存器是 CPU 中最快的存储，但数量**非常有限**（如 32 个）。
编译器必须决定：**哪些变量放在寄存器里？哪些 spill 到内存？**

```
变量很多，寄存器很少：
  int a, b, c, d, e, f, ... (20 个变量)
  vs
  R0, R1, ..., R7 (8 个寄存器)

→ 不可能都放寄存器 → 需要分配策略
```

### 图着色法 Graph Colouring

寄存器分配的标准算法，基于**图着色**：

```
步骤 1：构建干涉图 Interference Graph
  节点 = 变量 / 临时值
  边 = 两个变量不能共用同一个寄存器（因为它们的生命周期重叠）

步骤 2：图着色
  用 N 种颜色（N = 可用寄存器数）给图上色
  相邻节点不能同色
  如果成功 → 每种颜色 = 一个寄存器
  如果不成功 → 需要 spill（把一些变量放到内存）

步骤 3：Spill
  选择着色失败的变量 → 放到内存中
  每次使用该变量时 → 加载到寄存器（load），用完存回（store）
  然后重新尝试着色

例：
  a ←┐
     ├── 重叠 → a 和 b 不能同寄存器
  b ←┘
     ┌── 重叠 → b 和 c 不能同寄存器
  c ←┘
  
  干涉图：a — b — c
  2 种颜色：a = R0, b = R1, c = R0（a 和 c 不重叠，可复用）
```

### 图着色示例

```
代码：
  a = 1;          ; 定义 a
  b = a + 2;      ; 使用 a，定义 b
  c = a + b;      ; 使用 a, b，定义 c
  d = c + 1;      ; 使用 c，定义 d

生命周期 Liveness：
  a: live from line 1 to line 3
  b: live from line 2 to line 3
  c: live from line 3 to line 4
  d: live from line 4 onward

干涉图：
  a — b（重叠）
  a — c（重叠？a 到 line 3，c 从 line 3 开始，边界重叠 → 干涉）
  b — c（重叠）
  c — d（重叠）
  a — d（不重叠：a 在 line 3 结束，d 从 line 4 开始）
  b — d（不重叠）

着色（2 个寄存器）：
  a → R0
  b → R1
  c → R0（c 和 a 可共用：生命期不重叠）
  d → R1（d 和 b 可共用）

生成的代码：
  R0 = 1           ; a
  R1 = R0 + 2      ; b
  R0 = R0 + R1     ; c
  R1 = R0 + 1      ; d
  只用了 2 个寄存器！
```

### 寄存器分配的挑战

```
难点：
  1. 图着色是 NP-hard 问题（编译器用启发式算法）
  2. 函数调用时需要保存/恢复寄存器（caller-save vs callee-save）
  3. 有些寄存器有特殊用途（SP、FP、PC...）

Caller-save vs Callee-save：
  Caller-save：调用者负责保存（调用前 push，调用后 pop）
  Callee-save：被调用者负责保存（函数开头 push，结尾 pop）
```

### 📝 典型简答题：编译器优化与时间 Typical Short-Answer Q: Compiler Optimisations for Time

> 你反馈："编译器中这个将计算的算了对于时间的优化"

```
Q: "Explain how compiler optimizations affect the execution time of a program."
   "解释编译器优化如何影响程序的执行时间。"

Model answer / 参考答案：

Compiler optimizations target the Iron Law of processor performance:
编译器优化针对 Iron Law 的三个因子：

  Time = Instructions × CPI × ClockCycleTime

Key optimisations and their effects / 关键优化及其影响：

  ① Constant folding + propagation → ↓ Instructions
     常量折叠+传播 → 减少指令数（编译期算好常量表达式）

  ② Dead code elimination → ↓ Instructions
     死代码消除 → 减少指令数（删掉无用代码）

  ③ Strength reduction → ↓ CPI
     强度削弱 → 降低 CPI（x*2 → x<<1，移位比乘法快）

  ④ Instruction scheduling → ↓ CPI
     指令调度 → 降低 CPI（重排指令减少流水线 stall）

  ⑤ Loop unrolling → ↑ Instructions but ↓ CPI, net ↓ Time (trade-off)
     循环展开 → 指令数↑但 CPI↓，总时间可能减少（权衡）

Important insight / 关键 insight:
  The goal is to minimise total execution time, not instruction count.
  优化目标是总时间最小化，不是指令数最小化！
  Loop unrolling is a classic example of this trade-off.
  循环展开就是典型例子。

What does NOT affect execution time / 什么不影响执行时间：
  Removing comments, removing whitespace, renaming variables
  删除注释、删除空白、变量重命名 — 这些在词法分析阶段被处理，不影响机器码
```

```
Q: "Does removing comments from source code make the compiled program run faster?"
   "删除源代码中的注释是否能让编译后的程序跑得更快？"

Model answer / 参考答案：

False. Removing comments does NOT affect execution time.
假。删除注释不影响执行时间。

Comments are stripped during lexical analysis (tokenisation), before the AST is built.
They never appear in the intermediate representation or generated machine code.
注释在词法分析阶段被剥离，不进入 AST，不影响生成的机器码。

Therefore, they have zero impact on the number of instructions, CPI, or clock cycle time.
因此，注释对指令数、CPI、时钟周期完全没有影响。

(They may very slightly reduce compilation time, but not execution time.)

```

### ⚠️ Common Mistakes / 易错点
- **Boundary overlap / 边界重叠算不算干涉？** If var A's last use is at line N and var B is defined at line N, they **do NOT interfere** (can share register) / 不干涉，可共用
- **Graph colouring is NP-hard** — exam uses a simplified version; colour by descending degree / 考试用简化版
- **Spill is normal** — when there aren't enough registers, some variables go to the stack (spill) / 变量太多就 spill 到栈上，不是失败
- **Caller-save vs Callee-save**: caller-save registers are pushed BEFORE call; callee-save are pushed at function start / 调用者保存 vs 被调用者保存
